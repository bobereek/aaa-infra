# Embedding Service

## Краткое описание

Embedding Service построен на базе `FastAPI` и модели `rubert-mini-frida` для получения эмбеддингов текста.

Имеет 3 endpoint'а:

 1. /
 2. GET /health
 3. POST /embed

**Почему FastAPI?**

FastAPI один из самых быстрых Python-фреймворков. Для инференс-сервиса, где основную нагрузку берет на себя модель, важно, чтобы веб-слой вносил минимальные расходы.

Также в нем есть автовалидация инпута через Pydantic, что гарантирует, что модель не упадет из-за некорректного входного типа данных.

## Бенчмарк сервиса

Для тестирования сервиса был написан бенчмарк-класс. Тест имел два параметра: общее количество запросов и количество параллельных запросов.

Также я провел тестирование для **легких** (2 слова) и **тяжелых** (300 слов) запросов.

Вот результаты по выбранным мною метрикам.

### 1. Latency: P50 и P95

**Время, за которое пользователь получает ответ.**

- **P50** показывает медианное время ожидания запросов.
- **P95** показывает худший сценарий. Для инференс-сервисов это критично, так как один «тяжелый» запрос может заблокировать ресурсы для остальных.

В целом кривые P50 и P95 линейно растут близко друг к другу, что говорит о +- стабильной скорости работы сервиса.

**Приемлемый порог:**

- **Для P95: < 200–300 мс** (для легкой модели уровня `mini-BERT`).
- **Почему:** Эмбеддинги часто являются лишь частью пайплайна ML-сервиса. Если только получение вектора занимает >1 секунды (как на ваших графиках при нагрузке), всё приложение будет ощущаться «тормознутым».

При конкуренции около 15 для тяжелых запросов и 30 для легких запросов порог превышает допустимый.

**Что делать:**

1. **Квантование модели:** Конвертировать в `INT8` или `FP16`.
2. **Оптимизация кода:** Перейти на асинхронное взаимодействие, выполнять задачи параллельно.

---

### 2. RPS (requests per second)

**Количество запросов, которое сервис может успешно обработать за одну секунду.**

Это показатель масштабируемости. На ваших графиках видно, что после определенного порога RPS перестает расти и начинает падать, что говорит о насыщении ресурсов.

С повышением конкуренции RPS и выходит на плато около 18 тяжелых запросов и 47 для легких.

- **Цель:** Стабильный RPS без деградации при росте конкурентности.

**Что делать:**

1. **Request Batching:** Собирать нескольких запросов в один батч.
2. **Использование GPU:** Тесты проводились на CPU, поэтому если перенести модель на GPU, RPS заметно вырастут.

---

### 3. CPU/GPU Usage

**Насколько эффективно модель использует доступные вычислительные мощности.**

На графике "Mean CPU Usage" мы видим выход на плато в районе 90% при тяжелых запросах и 35-40% для легких.

**Хотим:**

- **70–80%** при пиковой нагрузке. Нужно оставлять запас на другие нужды, чтобы избежать резких просадок Latency из-за нехватки ресурсов.

**Что делать:**

1. **Вертикальное масштабирование:** Выделить больше ядер (CPU cores) на контейнер.

### 4. RAM Usage

**Объем памяти, необходимый для хранения весов в оперативной памяти и выделения буферов под вычисления.**

**Приемлемый порог:**

- **Стабильное использование < 80% от выделенного объема.** Резкие скачки могут привести к OOM (Out Of Memory) и падению сервиса.

**Что делать:**

1. **Ограничение размера батча:** Если используется батчинг, уменьшить его размер, так как RAM растет пропорционально размеру батча и длине текста.
